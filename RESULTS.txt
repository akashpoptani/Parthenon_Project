CONTEXT:
We are analyzing the Parthenon-VIBE AMR benchmark from the paper:
"Characterizing Adaptive Mesh Refinement on Heterogeneous Platforms with Parthenon-VIBE."

The paper studies Parthenon performance on heterogeneous CPU/GPU systems using:
- CPU: 96-core Intel Sapphire Rapids (SPR)
- GPU: NVIDIA H100
- Benchmark: Parthenon-VIBE / Burgers benchmark
- Metric: Figure of Merit (FOM), measured as zone-cycles/sec, And Total Time and Memory consumed

Key high-level findings from the paper:
1. GPUs perform well for large mesh blocks and enough work per kernel.
2. GPU performance collapses for small MeshBlockSize and deeper AMR levels.
3. The main bottlenecks are serial CPU-side work, ghost-zone communication, buffer packing/unpacking, load balancing, and AMR metadata management.
4. Increasing MPI ranks per GPU improves performance by reducing host-side serial bottlenecks, but GPU memory limits how many ranks can be used.
5. CPU performance scales more smoothly with rank count because it has much larger memory capacity and many CPU cores.

Below are the additional experimental results collected while exploring the paper.

OVERALL TAKEAWAYS FOR THE AGENT
============================================================

1. The core problem is not simply slow GPU kernels.
   GPU kernels are often a small fraction of total runtime. The major issue is CPU-side serial overhead, communication orchestration, AMR metadata management, and buffer handling.

2. Smaller MeshBlockSize is the worst case for GPUs.
   At MeshBlockSize = 8 or 4, GPUs can become slower than the 96-core CPU because there is too little work per block and too much communication/metadata overhead.

3. Deeper AMR levels hurt GPUs more than CPUs.
   More AMR levels increase refinement complexity, communication, and irregularity. CPUs tolerate this better because they can use many ranks and have much larger memory.

4. More MPI ranks per GPU help, but memory becomes the limiting factor.
   Increasing ranks improves performance by parallelizing host-side serial work, but memory usage increases due to MPI buffers, Open MPI overheads, and replicated Kokkos/Parthenon data structures.

5. RedistributeAndRefineMeshBlocks, SendBoundBufs, SetBounds, and ReceiveBoundBufs are critical optimization targets.
   These functions dominate runtime in difficult GPU configurations.

6. For SetBounds, SendBoundBufs, WeightedSumData, and FillDerived, the GPU kernel portion is small compared to the total function time.
   This suggests that optimizing only CUDA kernels will not solve the full problem. The agent should inspect CPU-side logic, metadata lookups, buffer initialization, fences, MPI progress, and synchronization.

7. CPU scaling is good until around 64 cores, then it flattens.
   This indicates a serial/synchronization floor even on CPUs.

8. Memory optimization is necessary for better GPU rank scaling.
   Kokkos memory consumes around 66-78 GB in the hard configuration, leaving limited room for MPI buffers and additional ranks. Reducing temporary/intermediate Kokkos allocations could allow more ranks per GPU and improve performance.

Observation:
The GPU kernels themselves show poor overall SM utilization, especially when MeshBlockSize decreases from 32 to 16. Total SM utilization drops from 23.4% for B32 to 19.1% for B16. Warp utilization also drops significantly from 95.3% to 76.3%, showing that smaller mesh blocks lead to less effective use of GPU threads.

CalculateFluxes is the dominant GPU kernel by duration. It takes 135.0 ms for B32 and 94.9 ms for B16, making it the largest contributor to CUDA kernel time. However, its SM utilization is only 32.3% for B32 and 27.9% for B16, and its SM occupancy is only about 24% in both cases. This suggests that the kernel is limited by occupancy and inefficient GPU execution rather than raw compute throughput.

The drop in warp utilization for CalculateFluxes is especially important. Warp utilization decreases from 94.1% for B32 to 67.6% for B16. This supports the paper’s argument that smaller mesh blocks create poor mapping between the AMR block structure and CUDA thread/block execution. Many GPU threads become inactive or do not perform useful work.

Memory bandwidth utilization is also low. The total bandwidth utilization is only 18.1% for B32 and 13.2% for B16. This means the kernels are not effectively using H100 HBM bandwidth, even though many of them have low arithmetic intensity and should be memory-sensitive. The likely reason is irregular/sparse memory access patterns and poor spatial locality across mesh blocks.

Several communication-related kernels, such as SendBoundBufs and SetBounds, have very low arithmetic intensity near 0.0 to 0.1 FLOPs/byte. These are mostly data movement kernels. However, their bandwidth utilization is still not close to peak, indicating inefficient memory access behavior rather than pure bandwidth saturation.

WeightedSumData and FluxDivergence have high SM occupancy and relatively high bandwidth utilization compared to other kernels. These kernels appear to map better to the GPU. In contrast, CalculateFluxes, FirstDerivative, MassHistory, and Est.Time.Mesh show very low SM utilization, making them important candidates for deeper GPU-side inspection.

Overall Takeaway:
The GPU bottleneck has two layers:
1. At the application level, most runtime is outside Kokkos kernels, dominated by CPU-side orchestration, communication, metadata handling, and AMR management.
2. Inside the GPU kernels, utilization is still poor. Smaller mesh blocks reduce warp utilization, SM utilization, and bandwidth utilization.

Optimization should therefore not only target CPU-side serial overheads but also the GPU kernel structure. In particular, CalculateFluxes should be inspected for register pressure, CUDA block shape, inactive warps/threads, memory access locality, and whether the Kokkos launch configuration matches the actual MeshBlockSize.
