Parthenon Discussion:

Summary of "Parthenon"
What’s the overall view of the work?
"Parthenon" is a performance-portable, block-structured adaptive mesh refinement (AMR) framework designed for high-performance computing (HPC). It is derived from the widely used ATHENA++ astrophysical magnetohydrodynamics (MHD) code but has been generalized to serve as a foundation for various multi-physics applications.
What domain is the work done in?
The work falls within the domain of high-performance computing (HPC) and scientific computing, specifically focusing on adaptive mesh refinement (AMR) for multi-physics simulations.
Is there any specific sub-domain that the work focuses on?
Yes, it focuses on performance portability in AMR-based simulations. It emphasizes efficient execution across different CPU and GPU architectures while minimizing data movement and computational overhead.
What problem/innovation is the work tackling?
The primary challenge is that existing AMR frameworks lack performance portability—meaning they do not efficiently utilize the diversity of modern computing architectures (e.g., CPUs, GPUs from different vendors). The work also addresses kernel launch overhead and inter-node communication bottlenecks in large-scale simulations.
How was that problem tackled before?
Other AMR frameworks like AMREX and UINTAH have attempted similar solutions but with trade-offs:
AMREX provides a more flexible mesh structure but increases complexity.
UINTAH uses KOKKOS internally but operates at a more fine-grained task level, which may lead to inefficiencies.
Is this a new problem?
No, performance portability in AMR has been a long-standing issue. However, the complexity of modern hardware has made this problem more critical at the exascale level.
Has this problem been solved at all?
Partially. Other frameworks have addressed individual aspects but do not provide a comprehensive solution like Parthenon.
Is this work a solution for a new problem or an already existing problem?
This work proposes a new solution to an existing problem by introducing Parthenon, which enhances portability while abstracting hardware-specific complexities.
Specifics of the Work
What is the problem?
AMR frameworks need to:
Be performance portable across different architectures (AMD, NVIDIA GPUs, x86, Power9 CPUs, etc.).
Reduce overheads from kernel launches and inter-node communication.
Be scalable to exascale supercomputers.
What is the solution?
Parthenon achieves these goals by:
Using KOKKOS for hardware abstraction.
Allocating all simulation data on the device to minimize host-device transfers.
Supporting logical packing of variables and mesh blocks to reduce kernel launch overhead.
Employing asynchronous, one-sided MPI communication for inter-node data transfer.
What did they use for the solution?
KOKKOS: A C++ library for performance portability across heterogeneous architectures.
ATHENA++: The base code from which Parthenon is derived.
Device-Resident Data Strategy: Ensures minimal data movement between host and device.
How was the solution implemented?
Abstracted loop structures to optimize execution across CPUs and GPUs.
Task-based execution model for handling complex dependencies.
Integration with existing AMR techniques like prolongation/restriction and load balancing.

1. What communication is being referred to?
The communication being referred to includes:
Between GPUs (Inter-GPU communication): When Parthenon runs on multi-GPU systems, mesh data needs to be exchanged between GPUs, which is handled using asynchronous MPI.
Between CPUs (Inter-CPU communication): Similar to GPUs, MPI is also used for CPU-based parallelism across multiple nodes.
CPU-GPU Communication (Intra-Node Communication): Data may need to be transferred between CPU and GPU memory, though Parthenon minimizes this by keeping data resident in device memory as much as possible.
Parthenon optimizes these communications by packing multiple mesh blocks into a single buffer and sending them asynchronously, reducing overhead caused by multiple small messages.

2. How do they demonstrate near-peak memory bandwidth efficiency?
Roofline Model Analysis: They compare the attained memory bandwidth of Parthenon against the theoretical peak bandwidth of the hardware.
Performance Scaling Experiments: They measure how memory-bound operations scale across different architectures (e.g., A100, V100, MI250X, CPUs).
Comparison to Baseline Codes: They compare Parthenon’s efficiency relative to Athena++ and K-Athena, highlighting reduced memory movement and higher utilization.
Parthenon prioritizes memory bandwidth efficiency by:
Minimizing memory movement (e.g., keeping all working data in GPU memory).
Using logical packing of variables to increase coalesced memory accesses.
Avoiding redundant copies between host and device memory.

3. What is the granularity of launching kernels for GPUs?
Kernels are launched per block pack (a group of multiple MeshBlocks).
MeshBlockPacks contain multiple MeshBlocks that are processed in a single kernel launch.
VariablePacks combine multiple variables into a single flattened index space, ensuring that multiple related computations are performed in the same kernel.
This reduces kernel launch overhead because:
Instead of launching a kernel for each individual block, multiple blocks are computed in one launch.
Kernel launch overhead on GPUs (which can be 5-7μs per launch) is minimized.

4. What is Block-Structured AMR? Are there other types?
Block-Structured AMR:
The computational domain is divided into blocks of uniform size.
Blocks are refined independently, forming a tree hierarchy (e.g., quadtree in 2D, octree in 3D).
Advantage: Easier load balancing and efficient memory management.
Other AMR Types:
Cell-Based AMR:
Individual cells (instead of blocks) are refined.
Used in codes like RAMSES and FLASH.
Disadvantage: Higher overhead due to more metadata per cell.
Patch-Based AMR:
Refinement occurs in arbitrary patches of varying shape and size.
Used in ENZO and PLUTO.
Disadvantage: More complex load balancing.
Parthenon uses Block-Structured AMR, as it balances flexibility and computational efficiency.

5. What is Kokkos?
Kokkos is a C++ performance portability framework that allows single-source programming across CPUs, GPUs, and other accelerators.
Key Features:
Execution Spaces: Defines where (CPU, GPU) code runs.
Memory Spaces: Defines where data is stored (host vs. device memory).
Execution Policies: Defines parallel execution strategies (e.g., parallel_for, parallel_reduce).
Memory Layouts: Controls data access patterns for optimal memory efficiency.
Views: Multi-dimensional array abstraction for portable memory management.
Parthenon relies on Kokkos to achieve performance portability across different supercomputers.

6. What happens if Device Memory runs out?
Memory Overflows are a concern for large-scale AMR simulations.
Parthenon’s Strategies:
Reducing memory footprint by sparse allocation of variables (allocating data only where needed).
Data compression using HDF5 compression for checkpointing.
Streaming Computation: Keeping only a subset of data in memory and streaming the rest on-demand.
Dynamic Memory Management: Adjusting the size of blocks to fit available memory.
Hybrid Execution (CPU-GPU sharing): If GPU memory is exhausted, some data can be kept on CPU RAM.

7. Is Device-to-Device Communication Allowed?
Yes. Parthenon uses asynchronous, one-sided MPI for GPU-to-GPU communication.
On systems with NVLink, Parthenon will use NVLink for direct GPU-to-GPU transfers.
Implementation Details:
Uses one-sided MPI with GPU-aware buffers.
Allocates communication buffers directly in device memory.
Uses CUDA-aware MPI or HIP-aware MPI to bypass host memory.
This reduces latency compared to traditional host-mediated MPI transfers.

Optimized for minimal data movement:

These techniques ensure load is evenly distributed, maximizing parallel efficiency.

1. Is CPU-CPU and CPU-GPU communication also asynchronous MPI?
CPU-CPU Communication (Inter-CPU): Yes, asynchronous MPI is used for communication across CPU nodes.
CPU-GPU Communication (Intra-Node): No, CPU-GPU communication typically involves synchronous memory transfers using CUDA/HIP memory copies rather than MPI. However, data transfers can be overlapped with computation using CUDA streams or HIP streams.
Parthenon minimizes CPU-GPU communication by keeping most of the data in device memory.

2. "Near-Peak Memory Bandwidth Efficiency" – Which Bandwidth?
They refer to on-device memory bandwidth, i.e., the bandwidth to access GPU memory (HBM) or CPU memory (DRAM).
Not host-to-device PCIe/NVLink bandwidth.
Not inter-CPU communication bandwidth.
Parthenon achieves high memory bandwidth utilization because:
Most operations are memory-bound (e.g., stencil-based PDE solvers).
Data stays in device memory, avoiding costly CPU-GPU transfers.

3. Is Parthenon memory-bound? Which figure shows that?
Yes, Parthenon is memory-bound because:
It performs stencil-based calculations (e.g., finite-volume methods).
It has low arithmetic intensity, meaning each operation moves more data than it computes.
Figures 8 and 9 show memory-bound behavior:
Figure 8 (Overhead of small blocks): Performance drops drastically with many small blocks, indicating kernel launch overhead dominates.

4. Do we launch kernels every timestep? Why?
Yes, kernels are launched every timestep because:
Each timestep updates the solution to a PDE.
Every cell’s values change, requiring new computations.
Even with all data in GPU memory, parallel updates must be applied to every MeshBlock.
Kernels are not only for initialization because:
Time Integration (RK2, RK3): Each timestep involves multiple stages of computation.
Mesh Refinement (AMR): Cells need to be interpolated/restricted dynamically.
Boundary Updates: Ghost cells must be filled each timestep.

5. Is Parthenon Patch-Based?
No, Parthenon is Block-Structured AMR, not Patch-Based AMR.
Block-Structured AMR: Mesh is divided into uniformly sized MeshBlocks.
Patch-Based AMR: Refinement happens in arbitrary-shaped regions.

Kokkos Views = Flexible multi-dimensional arrays that work across GPUs and CPUs.
Views abstract away hardware-specific memory layouts, enabling performance portability.

Mesh: Organized as a tree of MeshBlocks.
MeshBlock: Stores simulation data, MPI handles, ghost cells.
Cells: Data stored as multi-dimensional Kokkos Views.

8. What kind of messages are merged in MPI?
Boundary Exchange Messages: Ghost cell updates.
Mesh Refinement Messages: Coarse-to-fine or fine-to-coarse interpolations.
Particle Data Transfers: If simulations involve Lagrangian particles.
Merging reduces latency by minimizing MPI calls.

9. "Only necessary variables are communicated." Is this only ghost cells?
Yes, ghost cells are the primary data exchanged.
But also:
Particle data (in Lagrangian simulations).
Mesh refinement data (prolongation/restriction).
Flux corrections (for conservative methods).

10. How often is load balancing done? Does the user implement it?
Load balancing happens when AMR changes, i.e., when:
New MeshBlocks are refined or coarsened.
The workload becomes uneven.
Fully handled by Parthenon; users don’t need to implement it manually.

11. How does block transfer work in GPU-based systems?
If GPUs have NVLink, data is transferred directly GPU-to-GPU.
Otherwise, data moves via host memory (PCIe).
Transferred data:
Full block, or
Coarsened version (if refinement is needed at the new rank).

Yes, if a coarsened block is received, it must be refined again at the new location.

Responses to Your Questions:

1. What is a Stencil-Based PDE Solver?
A stencil-based PDE solver computes updates for each cell using neighboring cell values.
Used in finite-difference, finite-volume, and finite-element methods.
Common in fluid dynamics, weather modeling, and astrophysics.
Example: 5-Point Stencil for 2D Heat Equation
For a 2D grid with temperature u(x,y,t)u(x, y, t), update formula:
ui,jt+1=ui,jt+α⋅(ui+1,jt+ui−1,jt+ui,j+1t+ui,j−1t−4ui,jt)u_{i,j}^{t+1} = u_{i,j}^{t} + \alpha \cdot \left( u_{i+1,j}^{t} + u_{i-1,j}^{t} + u_{i,j+1}^{t} + u_{i,j-1}^{t} - 4u_{i,j}^{t} \right)
This involves reading five values per cell, computing one update, and writing one value.

2. Why Does Parthenon Have Low Arithmetic Intensity?
Arithmetic intensity = (Floating-Point Operations) / (Bytes Moved).
Stencil-based PDE solvers have low arithmetic intensity because:
Each update reads many values (neighboring cells).
Each update performs few operations (e.g., addition, multiplication).
More data movement than computation, making it memory-bound.

3. Why Are Kernels Launched Every Timestep?
Even though GPU memory (HBM) stores updated values, we still need kernel launches because:
Time Integration: Each timestep applies updates based on the PDE.
Data Dependencies: Next-timestep values depend on neighbor values from the previous timestep.
Boundary Communication: Halo (ghost) cells need to be communicated and updated.
Refinement/Coarsening: AMR dynamically changes resolution.
Why Can’t We Just Tell the GPU to Do Everything at the Start?
GPUs cannot predict future refinements in AMR.
Ghost cell exchanges need communication every timestep.
Different kernels handle different tasks (e.g., computation, communication).

4. What Are These Kernel Launches For?
Each timestep involves multiple kernel launches:
Computation Kernels: Solve PDEs on each MeshBlock.
Boundary Exchange Kernels: Update ghost cells (MPI communication).
AMR Refinement Kernels: Prolongation/restriction of MeshBlocks.
Reduction Kernels: Compute global quantities (e.g., CFL condition).

5. What Data Type Does Parthenon Use?
Kokkos Views use double precision by default.
Users can choose single (float) or double (double) precision.
Example:

7. How Often Does Refinement Happen?
Refinement does not happen every timestep.
It happens when needed, based on:
User-defined frequency (e.g., every 10 timesteps).
Error threshold criteria (e.g., gradient-based).

Responses to Your Questions:

1. Is Reading/Writing More Expensive than Computation?
Yes, in memory-bound problems like stencil-based PDE solvers, reading and writing (memory access) dominates over computation.
Memory Access:


Read 5 neighboring values per cell from memory.
Write 1 updated value per cell back to memory.
Total: 6 memory operations per cell.
Computation:


A stencil update usually involves a few floating-point operations (FLOPs), e.g., addition and multiplication.
Why is memory access the bottleneck?


HBM bandwidth is limited (e.g., ~900 GB/s on A100).
Compute units can perform thousands of FLOPs per cycle, but they wait for data from memory.
Loading ghost cells (MPI communication) is often more expensive than computing the update!
Conclusion:
 Yes, we spend more time reading ghost cells (communication) than computing the update itself.

2. Is Kernel Launch a Big Overhead in Parthenon?
Yes, kernel launches are a major overhead, especially for small blocks.
On GPUs, kernel launches take 5-7 μs per launch.
If many small MeshBlocks exist, kernel launch overhead becomes significant.
What percentage of time is spent on kernel launch overhead?
Figure 8 in the paper shows that performance drops by 82× when using many small blocks, mainly due to kernel launch overhead.
With buffer/block packing, Parthenon reduces the overhead to ~3.5×, making it comparable to CPU performance.
Optimizations to reduce kernel launch overhead:
MeshBlock packing: Combine multiple MeshBlocks into one kernel.
Variable packing: Pack multiple variables into one memory block.
Fused kernels: Merge computation and communication steps.

3. Can Device-Side Looping Be Implemented in Parthenon?
Yes, device-side looping (looping within a single kernel launch) can reduce kernel launch overhead.
Currently, Parthenon launches separate kernels per timestep.
Alternative: Use a single long-running kernel that:
Iterates over multiple timesteps inside device memory.
Avoids frequent host-device synchronization.
Challenges:
AMR requires dynamic refinement, which is hard to handle inside a single kernel.
Boundary updates (MPI communication) still need synchronization.

4. What Are Reduction Kernels?
Reduction kernels compute global quantities needed for the simulation.
 They perform parallel reductions across all MeshBlocks.
Examples of Reduction Kernels in Parthenon:
CFL Condition Calculation:


Finds the maximum velocity in the domain to determine the largest stable timestep.
Uses parallel_reduce to get global max velocity.
Conservation Checks:


Computes total energy/momentum to ensure physical conservation.
Error Estimation for AMR:


Computes gradients to check if refinement is needed.
Example in Kokkos (Parallel Reduction for CFL condition):
Kokkos::parallel_reduce("CFL_Condition", N, KOKKOS_LAMBDA(int i, double& max_v) {
    max_v = fmax(max_v, velocity[i]);
}, Kokkos::Max<double>(cfl_max));


5. What Precision Does Parthenon Use for Burgers’ Equation?
Parthenon defaults to double precision (double).
Users can switch to float for better performance if precision is not critical.

6. Do We Need to Communicate Ghost Cells During PDE Update?
No. Ghost cells are already present in HBM from previous updates.
Step 1 (Computation Kernel): Reads active + ghost cells from GPU memory.
Step 2 (Boundary Exchange): Sends ghost cells only after computation.
Why don’t we need communication during computation?
Each MeshBlock already has ghost cells stored in HBM.
Computation only reads ghost cells; it doesn’t modify them.

8. Does Restriction/Prolongation Happen Before or After Ghost Cell Communication?
Before sending data (coarse-to-fine).
After receiving data (fine-to-coarse).
How Refinement Kernel Works:
Restriction: Averages fine cells into coarse cells.
Prolongation: Interpolates coarse cells into fine cells.
Example (2× Refinement in 1D):
fine[i] = 0.5 * (coarse[i] + coarse[i+1]);


9. Summary of Kernels Launched Every Timestep
Compute Kernel (1 launch per MeshBlockPack)
Boundary Communication Kernel (1 launch per exchange)
Refinement Kernel (if AMR is triggered)
Reduction Kernel (1 launch for CFL/global values)
Total: 3-4 kernel launches per timestep.

Conclusion
Memory access dominates over computation in Parthenon.
Kernel launch overhead is a major bottleneck, mitigated by packing techniques.
Ghost cells are read from GPU memory, not communicated during computation.
Reduction kernels compute CFL condition and global properties.
AMR refinement includes restriction/prolongation before/after boundary communication.
